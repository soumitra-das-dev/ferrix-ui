# Ferrix Architecture Specification

## 1. Overview & Core Philosophy
**Ferrix** is a statically compiled Android UI framework designed for zero-overhead, highly reactive mobile applications. It enforces **Architecture A**:
- **Rust owns**: Application logic, component tree lifecycle, fine-grained reactive state, reconciliation, layout computation, async scheduling, and networking.
- **Kotlin owns**: Android UI lifecycle, native View rendering, frame scheduling (V-Sync), ephemeral interaction state (focus, selection, scroll position, gesture velocity, animation ticks), and platform SDK adapters.
- **Ahead-of-Time Compilation**: No JavaScript engine (Hermes/V8), no bytecode interpreter, and no runtime reflection. Developer `.fsx` code compiles directly to native Rust machine code.
- **Batched Wire Protocol**: Rust sends batched, typed UI patches over JNI. Rust never issues individual drawing commands and never touches Android Views directly.

```
┌────────────────────────────────────────────────────────┐
│                      Rust Core                         │
│  ┌──────────────┐   ┌────────────────┐   ┌───────────┐ │
│  │ FSX Codegen  │──▶│ Ferrix Runtime │──▶│ Taffy     │ │
│  │ (Components) │   │ (Signals/VDOM) │   │ Layout    │ │
│  └──────────────┘   └────────────────┘   └───────────┘ │
│                            │                           │
│              Batched UI Patches (DirectByteBuffer)     │
└────────────────────────────┼───────────────────────────┘
                             ▼ JNI Boundary
┌────────────────────────────────────────────────────────┐
│                   Kotlin / Android                     │
│  ┌──────────────────────────────────────────────────┐  │
```

## 2. Non-Negotiable Design Rules

### Rule 1: Three Independent Contracts
1. **Developer API (`*.fsx`)**: Declarative component syntax, JSX-like elements, static typing, and hooks.
2. **Runtime API (`ferrix-core`, `ferrix-reactivity`)**: Signal graph, hook memoization, keyed reconciliation, scheduler.
3. **Renderer Protocol (`ferrix-renderer-protocol`)**: Zero-dependency crate defining typed binary patches, node operations, and UI event structures.
*Compiler, runtime, and platform renderer can each be replaced without touching the others.*

### Rule 2: Fine-Grained Reactivity
State changes update **only dependent nodes**. There is no full-component re-render and no full-tree virtual DOM diff pass. Reactive signals notify fine-grained property subscribers, producing minimal, targeted patch entries.

### Rule 3: JNI Efficiency & Memory Model
- **Minimal Call Entry Points**: High throughput achieved through batched command buffers instead of Chatty JNI.
- **No Ad-Hoc JSON**: Payloads are packed binary structures over `DirectByteBuffer` or raw pointer blocks with length headers.
- **Stable Node IDs**: Every rendered element receives a unique, stable `u64` identifier generated by Rust.
- **No `@CriticalNative` for general UI**: JNI calls respect Android memory safety and thread transitions.
- **No Panics Across FFI**: All Rust JNI exports catch panics with `std::panic::catch_unwind` and propagate structured error codes.

### Rule 4: Threading Architecture
- **Android Main Thread**: Dedicated exclusively to native View tree operations, Android Choreographer frame callbacks, and input dispatch. It **never** blocks on Rust calculations.
- **Rust Runtime Thread**: Executes components, manages the dependency graph, runs reconciliation, and queues patch buffers.
- **Rust Async Pool (`tokio`)**: Handles background tasks, HTTP requests, and WebSocket connections. Async tasks are cancelled automatically upon component unmount to prevent updating destroyed nodes.
- **Boundary Invariant**: Rust never holds direct Java View references or calls View methods from background threads.

### Rule 5: Layout Authority
- **Single Source of Truth**: Rust computes exact node geometry using **Taffy** (Flexbox/Grid layout engine).
- **Kotlin Applies Only**: Kotlin receives computed frames `(x, y, width, height)` and sets View layout parameters or calls `layout()`. There is no competing Android `onMeasure`/`onLayout` pass for Ferrix elements.
- **Environment Context**: Rust receives screen density (`dp` to `px`), font scale (`sp`), system window insets, and layout direction (`LTR` vs `RTL`) from Kotlin.

### Rule 6: Animation Mechanics
Animations execute frame-by-frame on Android using native animators (`ValueAnimator`, `Choreographer`) or RenderThread animations. Rust sends target values, curves, and durations; Kotlin executes the frame loop and notifies Rust only of state triggers or completion events.

### Rule 7: Platform SDK Adapters
Platform APIs (CameraX, Location Services, Sensors, Microphone, Storage, Biometrics, Permissions) are implemented as Kotlin adapters exposed via request/response envelopes and custom hooks (e.g. `useLocation()`). All requests are lifecycle-bound, support user denial, and honor explicit cancellation tokens.

### Rule 8: Abstraction of Views
The renderer contract targets standard Android Views (`android.view.ViewGroup`, `android.widget.TextView`, etc.) through an abstract `FerrixRenderer` interface, ensuring future backends (e.g., Jetpack Compose or Canvas rendering) can be plugged in without changing Rust code.

### Rule 9: Rust Networking & Security
HTTP networking runs in Rust via `reqwest`/`tokio`, configured to respect:
- Android system trust store (via platform certificate extraction or system keystore bindings).
- Platform proxy settings (HTTP/HTTPS/SOCKS).
- Android Network Security Config (cleartext traffic permissions, certificate pinning).

### Rule 10: Hybrid State Ownership
- **Rust owns**: Business logic, application state, network cache, component state, form validation rules, and structural navigation.
- **Kotlin owns**: Ephemeral native UI state (text selection, soft keyboard IME state, active scroll offsets, touch fling physics, focus indicators).
